# 实现方案：探针延迟与丢包显示（v1.11.0）

> 给实现者（AI 编码助手或人类开发者）：请先通读本文和根目录的 `AGENTS.md`，再动手。
> **在 v1.10（`docs/plans/v1.10-anti-spam-ux.md`）合并之后，从最新 `main` 开始做。**
> 遵守 `AGENTS.md` 的规定：**不能凭猜测解析探针接口**。下面的接口格式，是在作者本人的 Komari 1.5.0（`1.5.0-fix1`）上实际请求得到的；其他版本和其他探针，必须先拿到真实返回再适配。

## 目标

探针页的每个节点，显示各条线路的**延迟和丢包**，例如：

```text
📶 浙江电信   219 ms   丢包 25%
📶 浙江移动   105 ms   丢包 0%
```

v1.11 **只支持 Komari**。哪吒等其他探针，等有用户提供真实接口返回后再加。

## 一、Komari 的延迟数据接口（已实测）

数据来自 Komari 后台配置的「延迟监测任务」（Ping Task，每个任务对应一条线路，比如「浙江电信」「浙江移动」）。

### 1. 全部节点的统计：`public:getPingMetricStats`（主用）

一次请求就能拿到**所有节点、所有线路**的统计，优先用它。

```http
POST <探针地址>/api/rpc2
Content-Type: application/json

{"jsonrpc":"2.0","method":"public:getPingMetricStats","params":{"hours":1},"id":1}
```

实测返回（节选）：

```json
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "start": "2026-11-26T16:52:15Z", "end": "2026-11-26T17:52:15Z", "interval_seconds": 60,
    "stats": [
      {
        "entity_id": "496c4866-63b6-4025-b90a-bd7b1d0d6fd2",
        "task_id": "17", "name": "浙江移动", "type": "tcp", "interval": 300,
        "total": 12, "valid": 12, "loss": 0,
        "min": 40, "max": 65, "avg": 47.166666666666664, "latest": 41,
        "p50": 47.17, "p99": 47.17, "stddev": 0
      }
    ]
  }
}
```

- `entity_id` 就是节点的 `uuid`，和现有节点数据（`normalizeNodeMetrics` 里的 `uuid`）对得上。
- `loss` 是百分比（0–100），延迟单位是毫秒。
- 节点没有配置任何延迟监测任务时，`stats` 里就没有它。

### 2. 单个节点的明细：`GET /api/records/ping?uuid=<uuid>&hours=1`（仅供参考，本版本不使用）

```json
{
  "data": {
    "count": 24,
    "basic_info": [{ "client": "<uuid>", "loss": 12.5, "min": 64, "max": 310 }],
    "tasks": [
      { "id": 8, "name": "浙江电信", "type": "tcp", "interval": 300, "avg": 219, "loss": 25, "min": 135, "max": 310, "total": 12 },
      { "id": 17, "name": "浙江移动", "type": "tcp", "interval": 300, "avg": 105, "loss": 0, "min": 64, "max": 215, "total": 12 }
    ],
    "records": [
      { "task_id": 17, "time": "2026-11-26T17:46:00Z", "value": 69, "client": "<uuid>" },
      { "task_id": 8, "time": "2026-11-26T17:06:00Z", "value": -1, "client": "<uuid>" }
    ]
  },
  "status": "success"
}
```

- `records[].value` 为 **-1 表示这一次测量失败（丢包）**。
- 不带 `uuid` 请求会报错「UUID or task_id is required」。

### 3. 任务列表：`public:getPublicPingTasks`（可选）

返回所有任务的 `id`、`name`、`type`、`interval`、`weight`，以及 `clients`（参与这个任务的节点 uuid 列表）。可以用 `weight` 决定线路的显示顺序。

## 二、后端（`src/worker/komari.js`）

1. Komari 适配器拉取节点数据时，**并行**再请求一次 `public:getPingMetricStats`，参数 `{"hours": 1}`。
   - 请求失败、方法不存在（JSON-RPC 返回 `error`），或者超时，都**静默忽略**，节点数据照常返回，只是没有延迟信息。**延迟数据拿不到，绝不能让整个探针显示「无法连接」。**
   - 超时用独立的、较短的时间（例如 4 秒），不要拖慢节点数据。
   - 鉴权：和现有 Komari 请求用同一套请求头（`buildAuthHeaders`），私有探针也能拿到。
2. 把统计挂到对应节点上，节点对象新增字段：

   ```js
   latency: [
     { name: '浙江电信', type: 'tcp', avg: 219, min: 135, max: 310, latest: 135, loss: 25 },
     // ...
   ]
   ```

   - 数值四舍五入到整数，`loss` 保留一位小数。
   - 按任务的 `weight` 排序（取不到就按名字排序），每个节点最多保留 6 条线路。
   - 线路名称做长度截断（32 个字符），前端显示时照常转义。
3. **备用方案**：`public:getPingMetricStats` 不存在（较老的 Komari）时，**不要**为每个节点逐个请求 `/api/records/ping`（节点多时子请求太多）。直接不显示延迟，并在设置页「测试探针连接」的结果里提示「当前 Komari 版本不支持批量延迟统计，升级 Komari 后可显示延迟」。
4. **缓存**：延迟数据跟随现有探针缓存（`cache:komari_probe`）一起存，**不新增 KV 键、不增加写入次数**。Komari 每 5 分钟才测一次延迟，如果后续需要单独控制刷新频率，也只能放在同一个缓存对象里。
5. 演示模式（`getDemoKomariNodes`）给示例节点加上合理的假延迟数据，方便没接探针的人预览效果。
6. 其他探针类型（`nezha`、`nodeget`、`json`）的节点 `latency` 一律为空数组，界面不显示这一块。

## 三、前端（`web/src/components/ProbeTab.jsx`）

1. **节点卡片**：在 CPU、内存这些指标下面，每条线路一行：

   ```text
   📶 浙江电信   219 ms   丢包 25%
   ```

   - 显示 `avg`。鼠标悬停（或点击展开）显示「最低 / 最高 / 最近一次」。
   - 颜色：平均延迟 < 100 ms 绿色，100–200 ms 黄色，> 200 ms 红色。丢包 > 10% 时丢包数字标红，为 0 时显示淡色。
   - `latency` 为空时整块不显示。
2. **节点概要**（列表、紧凑视图）：显示平均延迟最低的那条线路，例如「📶 105 ms」。
3. **不做延迟曲线**：站长明确表示只需要看到平均延迟和丢包，测量频率无所谓。本版本**不实现**曲线，也**不新增** `/api/probe/latency/:uuid` 代理接口，保持简单。
4. 深色、浅色主题都要好看，手机屏幕上不溢出。

## 五、测试（`tests/worker.test.js`）

用上面第一节的**真实返回结构**做测试数据。现有测试一个都不能删、不能改弱。新增：

1. 统计正确挂到对应 `uuid` 的节点上；数值取整，`loss` 保留一位小数，按 `weight` 或名字排序，最多 6 条。
2. `public:getPingMetricStats` 返回 JSON-RPC `error`、HTTP 错误或超时时，节点数据照常返回，`latency` 为空，**`protocol` 不能变成 `error`**。
3. 没有配置延迟任务的节点，`latency` 为空数组。
4. 非 Komari 探针，`latency` 为空数组，并且**不会发起**延迟请求。
5. 延迟数据和节点数据存在同一个缓存键里，没有新增 KV 写入。

**验收**：`npm test && npm run build` 全部通过。合并后在作者的 Bot 上验证：探针页能看到「浙江电信」「浙江移动」的延迟和丢包。**前提是 Worker 能连通 Komari**（目前有一个尚未解决的网络超时问题，与本功能无关）。
